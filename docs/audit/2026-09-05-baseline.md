## 契约与能力核验

完整 HTTP 清单见 `http-contracts.md`。请求、响应 DTO 的唯一依据仍是两个 `.api` 文件，字段含义须结合 Mapper 和 RPC 授权验证。

| 边界 | 核验结果 / 前端决定 |
| --- | --- |
| App / Admin | `/api/v1` → 8002；更长前缀 `/api/v1/admin` → 8001，必须优先匹配 |
| 成功 / 失败 | 成功直接返回 DTO；错误 `{code,message}`，不增加 `data` 包装 |
| 枚举 / 时间 | 小写 snake_case / UTC RFC3339 |
| 身份 | Authorization 透传；UserIdentity / AdminIdentity 提前鉴权，下游 RPC 仍是最终边界 |
| 语言 | `cpp20-v3`、`go-v3`；与题目 `allowed_languages` 取交集，不启用 SPJ / 交互题 |
| 比赛题面 | `GET /problems/:problem_id?contest_id=...` 已有，不能通过改为公开题目绕过权限 |
| 提交 | `client_request_id` 是用户作用域幂等键；`source_code` 按 UTF-8 字节校验，最大 1 MiB，部署可更小 |
| int64 | JSON 数字可能超过 JS 安全整数；前端必须在解析阶段无损处理，不能先 `JSON.parse` 后转字符串 |
| Token | 首版仅内存、App/Admin 独立；刷新页面需重新登录，禁止默认持久化 Refresh Token |
| 缓存 | 会话变更清空对应缓存；迟到的刷新/请求不能恢复已退出的身份 |
| 技术方案 | 单个 `web/` React + TypeScript + Vite 工程，依赖锁定，中文界面；不改造 RPC 架构 |

## 已确认缺口与优先级

1. P0：无浏览器前端，M1–M4 页面和真实浏览器验收尚未实现。
2. P0：Docker 验收脚本仅设置 Submit DSN，未执行 Problem / Contest 的真实数据库集成；普通 race CI 会跳过这些测试。
3. P0：`make up` / dev-services 不含前端和 Worker，不能称为全栈就绪；缺少浏览器演示数据与完整闭环验收入口。
4. P1：CI 缺少显式 `go build ./...`，无前端静态检查和浏览器检查；完整 Docker 验收仅手动执行。
5. 待验证：预签名上传的浏览器可达性 / CORS；三种榜单和封榜浏览器表现；SMTP、备份恢复、负载排空、权限与异常体验。

## 负载验证方案（未执行）

在独立测试环境、固定语言镜像、Worker 并发 2 下，先以 5 个测试用户各提交 4 个已知 AC 程序（C++20 / Go 各半），再以 10 个用户各 10 次执行；记录机器、镜像摘要、起止时间、每个幂等键与终态计数，但不记录源码或 Token。观察窗口 10 分钟，HTTP 读取 p95 预算 1 秒、提交接收 p95 预算 2 秒；正确性门槛为任务无丢失、无重复终结、最终队列排空。以上仅为待验证预算，不是性能结论或生产 SLA；并发负载不能与安全计时验收同时运行。
