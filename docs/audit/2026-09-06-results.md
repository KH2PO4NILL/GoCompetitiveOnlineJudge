## 修复的主要问题

1. **HTTP 凭据泄露风险**：本地 go-zero 的默认访问日志会在 5xx 时转储请求，Verbose 模式还会转储响应；关闭该内容日志并通过统一构造器强制执行，不依赖部署者记得修改 YAML。新日志只保留方法、状态、耗时及上下文关联信息；测试验证密码、Bearer、Cookie、查询串、User-Agent 和响应内容不进入日志。
2. **敏感响应缓存**：两个网关统一设置 `Cache-Control: no-store` 和 `X-Content-Type-Options: nosniff`，覆盖正常业务响应和路由内错误响应。
3. **时间边界**：RFC3339 语法合法不意味着 protobuf Timestamp 合法；拒绝 year 0000，以及时区换算后超出 year 0001–9999 的时间，保留 optional 未传语义。
4. **通测覆盖缺口**：旧隔离脚本仅连接 Submit Model；现在同时执行题目版本 / 发布快照、上传事务回滚、比赛报名与各模式榜单 / 冻结事务、提交租约与幂等事务。保留 RocketMQ 本地替换模块。
5. **前端身份与精度边界**：刷新单飞、旧 401 不重复轮换、退出取消请求、迟到响应不可恢复旧身份、App/Admin 缓存独立；int64 在解析时无损保留，写回 JSON 数字；未知结果不自动重发写请求。
6. **可复现检查**：安装 npm 依赖后，某个依赖携带的 Go 示例原本会被根 `go test ./...` 扫入；使用 `web/go.mod` 标记遍历边界，使后端检查不依赖是否安装过前端依赖。

## 失败记录与未消除的不确定性

- 第一轮 Docker 脚本运行时被编辑，尾部读取错位，退出 127；这是本次操作造成的无效运行，不作为代码失败或成功证据。之后在脚本稳定的状态重新完整执行。
- 一次旧诊断复测在最终 `Cleanup` 断言失败；旧错误统一写作 “sandbox container leaked”，不能区分实际容器残留和 Docker API 错误。没有足够证据追溯当次原因。补充逐场景与最终详细断言后，完整语言 / 安全 / 恢复矩阵通过；未放宽断言、增加网络权限或跳过沙箱校验。此偶发失败仍需后续运行观察，不能宣称已定位并根治运行时泄漏。
- 浏览器初次运行受缺失系统库影响；随后两次因测试定位器非精确匹配失败，最终修正定位器并在真实浏览器通过，不通过删除业务断言来规避失败。
- Auth 隔离脚本初版误将 MySQL 初始化阶段的 Unix socket 临时服务当成就绪，随后改为 TCP 就绪；最终运行通过。清理加入匿名卷删除，仅清理本次拥有的资源；未对机器既有的匿名卷执行全局 prune。
- 本地测试结果不等于 GitHub 全部分支 CI 已通过。代码分支推送后 GitHub 工作流已启动；历史中间分支可能包含后续分支才修正的测试，最终以待合并分支对应工作流结果为准。
